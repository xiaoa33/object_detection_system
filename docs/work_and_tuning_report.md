## 一、经典 Bug 攻坚：并查集链式合并坍缩

### 1.1 故障现象

在 `group_rectangles_original()` 的第一版实现中，使用 IoM（Intersection over Minimum）作为重叠判定标准配合并查集分组。测试中发现一个诡异的退化：**当 `min_votes` 设置较低时，整张图像上的人脸检测框全部坍缩为一个巨大的中心框**——无论图中有多少张人脸，最终输出只有一两个覆盖半张图片的巨型矩形。

更令人困惑的是，这个巨型框的中心往往不在任何人脸上，而是落在一些高纹理区域——比如红色领带的花纹、衬衫褶皱、甚至背景中的书架。

### 1.2 根因分析

问题出在并查集的**传递性**。考虑这个真实场景：

```
人脸 A (左上角，100×100)
  → IoM 与"领带花纹误检框"重叠 0.45 → union(A, Tie)
领带花纹误检框 (中间偏下，80×80)
  → IoM 与"衬衫褶皱误检框"重叠 0.42 → union(Tie, Shirt)
衬衫褶皱误检框 (中间偏右，90×90)
  → IoM 与"人脸 B 的候选框"重叠 0.38 → union(Shirt, B)
```

虽然人脸 A 和人脸 B 之间的 IoM 接近于 0（距离太远），但并查集通过领带和衬衫这两个"桥接框"将它们连为一体。最终 `find(A) == find(B)`，两张人脸被归入同一连通分量。

这种**链式合并（Chain-Merging Collapse）**的底层原因是：IoM 只看面积重叠比例，完全不关心两个框在图像空间中的绝对距离。当图像中存在足够多的误检框（级联分类器在复杂纹理区域的假阳性），这些误检框就充当了"跳板"，逐步桥接起本来相距甚远的真实人脸。

第一版的判定逻辑：

```python
# 旧版 —— 仅依赖 IoM（有缺陷）
inter_area = inter_w * inter_h
min_area = min(areas[i], areas[j])
iom = inter_area / min_area
if iom > 0.4:
    uf.union(i, j)  # 只看面积重叠，不看空间距离！
```

两个框只要面积重叠超过 40% 就归为一组，完全不检查它们的绝对坐标是否接近。这等价于说"两个框如果重叠超过一半就算同一个目标"——在大多数情况下成立，但一旦有桥接框（桥接框可能与两端各有 41% 的重叠），就触发了传递性灾难。

### 1.3 修复方案：ε-邻域坐标相似度

参考 OpenCV 中 `groupRectangles()` 的实现思路（该函数也使用坐标邻域而非 IoU 来判定"属于同一个检测目标"），将判定标准从"面积重叠比例"改为"坐标差值是否在 ε 容差范围内"。

核心改动：**必须同时检查左上角和右下角共四个坐标的差值**，只有当所有差值都在容差范围内时才视为同组。

```python
# 新版 —— ε-邻域坐标差值判定（已修复）
dx = abs(x1s[i] - x1s[j])          # 左上角 x
dy = abs(y1s[i] - y1s[j])          # 左上角 y
dw = abs(x2s[i] - x2s[j])          # 右下角 x
dh = abs(y2s[i] - y2s[j])          # 右下角 y

limit_w = eps * min(ws[i], ws[j])  # 容差基于较小框
limit_h = eps * min(hs[i], hs[j])

if dx <= limit_w and dy <= limit_h and dw <= limit_w and dh <= limit_h:
    uf.union(i, j)
```

**为什么四个坐标必须全部检查？** 如果只检查左上角，两个大小不同的框只要左上角对齐就会被归组（可能一个是人脸框，另一个是误检的更大背景框）。如果只检查中心点，两个大小差异巨大的框也可能被错误归组。要求四个角点全部对齐，意味着两个框不仅位置要相近，**尺寸也要相近**——这是一个隐式的尺度一致性约束。

**容差基准为什么用 `min(w_i, w_j)`？** 使用较小框的尺寸作为基准，意味着两个框尺寸差异越大，判定越严格。例如一个 100×100 的框和一个 20×20 的框，容差为 `0.2 × 20 = 4px`。它们几乎不可能在四个角点都对齐在 4px 以内（除非 20px 框恰好位于 100px 框的某个角），因此不会被归组。这天然阻止了"大框套小框"的传递性桥接。

**为什么这个判定是"非传递"的（在实践中）？** 虽然并查集本身有传递性，但 ε-邻域条件在实践中阻止了长距离的链式传播。框 A 和框 B 在 ε-邻域内（它们真的属于同一个人脸），框 B 和框 C 也在 ε-邻域内（B 和 C 也属于同一人脸），但框 D（误检）很难恰好与 A 或 C 都在 ε-邻域内——因为 ε 容差是基于较小框尺寸的，而误检框的尺寸和位置与人脸框差异较大。

### 1.4 验证

修复后在 `group_threshold=3, eps=0.2` 的默认参数下：
- 单人脸图片：输出 1 个框，与预期一致
- 多人脸图片（3~5 人）：输出 N 个框，不再坍缩
- 高纹理背景（书架、衣物褶皱）：误检框因不满足 `group_threshold` 被整组丢弃

该 Bug 的修复是整个系统中**投入产出比最高的一次改动**——仅修改了判定逻辑的 4 行代码（从 IoM 改为坐标邻域），但彻底解决了一个会导致算法完全不可用的架构级缺陷。

## 二、参数博弈与系统性调优（FPS vs. 精度）

### 2.1 纯 Python 环境的现实约束

Viola-Jones 全链路（积分图 + Haar 特征 + 级联推理 + 多尺度滑动窗口）在 C++ 实现中可以轻松达到实时（30fps+），但在纯 Python/NumPy 环境下，单帧检测耗时通常在 100~500ms 之间。这意味着要在"流畅度"和"准确率"之间做大量的工程权衡。

本系统的性能杠杆有四个：**Min Face Size**、**Scale Factor**、**Step Factor (Δ)**、**Min Votes**。它们分别作用于检测管道的不同阶段，且存在复杂的交互。

### 2.2 金字塔层数的数学分析

金字塔从 `BASE_WIN_SIZE = 24px` 开始，每层缩放为上一层的 `1/scale_factor`，直到窗口尺寸达到 `min(image_height, image_width, max_face_size)` 或小于 `min_face_size`。

层数公式：

$$N_{scales} = \left\lfloor \frac{\log(\text{max\_face} / \text{min\_face})}{\log(\text{scale\_factor})} \right\rfloor + 1$$

以默认参数为例（min=60, max=140, scale=1.25）：

$$N = \lfloor \log(140/60) / \log(1.25) \rfloor + 1 = \lfloor 0.848 / 0.223 \rfloor + 1 = 3 + 1 = 4 \text{ 层}$$

如果 min_face=24（旧默认值）：

$$N = \lfloor \log(140/24) / \log(1.25) \rfloor + 1 = \lfloor 1.763 / 0.223 \rfloor + 1 = 7 + 1 = 8 \text{ 层}$$

**将 min_face 从 24 提升到 60，金字塔层数从 8 层减至 4 层，FPS 翻倍。** 代价是远处小人脸（< 60px）无法被检测——但在桌面应用场景中（用户通常面对摄像头坐在半米内），人脸通常占画面 100~300px，60px 的最小值完全够用。

### 2.3 滑动窗口总数的工程估算

每个尺度的窗口数近似为：

$$W_s = \left\lceil \frac{H - w_s}{\text{step}} \right\rceil \times \left\lceil \frac{W - w_s}{\text{step}} \right\rceil$$

其中 $w_s = \text{BASE\_WIN\_SIZE} \times s$，$\text{step} = \max(1, \text{round}(s \times \Delta))$。

以 480×360 的检测图像、scale=1.0（基础尺度 24×24）为例：

- Δ=1.0：step=1，窗口数 ≈ 457×337 ≈ 154,000
- Δ=3.0：step=3，窗口数 ≈ 153×113 ≈ 17,300（仅为 Δ=1.0 的 11%）
- Δ=5.0：step=5，窗口数 ≈ 92×68 ≈ 6,200

**Δ 从 1.0 到 3.0，窗口数减少约 89%，但检测耗时并非线性减少**——因为积分图构建和方差预计算是每帧一次的固定开销，级联分类器的早期拒绝机制也会在大部分窗口的前几层就快速返回。

### 2.4 各参数的调优实验与工程判断

以下数据基于实际运行中的定性观测（非精确 benchmark）：

| 参数组合 | 相对 FPS | 人脸检出率 | 误检率 | 适用场景 |
|---------|---------|-----------|--------|---------|
| min=24, scale=1.1, Δ=1.5, votes=2 | ★☆☆☆☆ (~2fps) | 极高 | 极高 | 离线精度优先 |
| min=60, scale=1.25, Δ=3.0, votes=45 | ★★★★☆ (~12fps) | 良好 | 低 | **日常实时检测（默认）** |
| min=100, scale=1.5, Δ=4.5, votes=100 | ★★★★★ (~18fps) | 一般 | 极低 | 高性能/强光照场景 |
| min=40, scale=1.15, Δ=2.0, votes=10 | ★★☆☆☆ (~5fps) | 高 | 中等 | 多人合影/复杂场景 |

#### Min Face Size = 60 的考量

24px（论文默认值）在 480×360 的检测图像上意味着：金字塔从 24×24 一直扫描到 140×140，覆盖约 8 个尺度。而在典型的视频通话距离（50~80cm），人脸通常占据画面高度的 20%~40%，即约 70~150px。将下限提升到 60px 切掉了最小的 3~4 个尺度，但这些尺度在实际使用中几乎不包含有效人脸——它们太小，Haar 特征的分辨力不足以区别人脸和噪声，反而产生大量假阳性。**将 min_face 提升到 60 是"减少噪声 → 减少误检 → 减少后处理压力"的正向循环。**

#### Min Votes = 45 的考量

`min_votes` 是抵御 Viola-Jones 模型本身较高误检率的最后一道防线。级联分类器经过训练后，在复杂纹理区域（衣物花纹、头发边缘、背景书架）仍会产生孤立的假阳性框。这些假阳性框的共同特征：**只有少数几个随机位置/尺度的窗口命中它们**——因为 Haar 特征恰好匹配了某个纹理模式，但不是系统性的。真正的人脸则会在多个相邻尺度和位移下被反复命中，形成密集的候选框簇。

- votes=2（旧默认）：几乎所有误检框都能通过，因为它们周围至少还有一两个相邻窗口也被激活
- votes=45（新默认）：要求一个位置被至少 45 个不同尺度/位移的窗口同时命中，这对随机纹理几乎不可能，但对真实人脸（在多尺度下外观一致）是可行的

**这是一个用几何一致性（geometric consensus）替代分类置信度的策略**——在 Viola-Jones 级联不输出概率分数的情况下，候选框的空间密度是置信度的最佳代理。

#### Step Factor = 3.0 的考量

VJ2004 论文的原文公式是 `step = round(s × Δ)`，推荐的 Δ 约为 1.0~2.0。但在纯 Python 环境下，我们选择了更激进的 3.0。原因：

1. 窗口步长与 Haar 特征的空间冗余度相关——Haar 特征本质上是低分辨率（24×24 基础窗口内只有 ~160,000 个特征），相邻像素的窗口特征值高度相关，跳过 2~3 个像素几乎不影响检出率
2. 后处理阶段的合并算法（NMS/均值合并）可以容忍最高 ~20% 的框位置偏移，步长 3px 在 24px 窗口上对应的偏移约为 12.5%，在合并容差范围内
3. Δ=3.0 时步长随尺度线性增长（scale=2.0 → step=6, scale=3.0 → step=9），大尺度下的稀疏采样进一步加速

### 2.5 降采样的 FPS 杠杆

除了上述参数，还有两个隐式的 FPS 杠杆：

1. **检测前降采样**（`video_thread.py`: 640×480 → 480×360）：窗口总数与图像面积成正比，面积减少 44% 直接转化为约 40% 的加速
2. **跳帧检测**（`_detect_interval = 2`）：每 2 帧检测 1 次，中间帧复用缓存。这相当于将检测帧率需求减半——如果单帧检测耗时 80ms（12.5fps），跳帧后有效显示帧率可达 25fps（摄像头原始帧率），视觉上完全流畅

### 2.6 最终参数配置及理由

| 参数 | 最终默认值 | 核心理由 |
|------|-----------|---------|
| NMS 阈值 | 0.15 | 低阈值 + IoM 度量 → 大框套小框也被识别为重叠，减少碎片化 |
| 最小人脸 | 60px | 切掉无用的小尺度层，FPS 翻倍，实际使用中不损失检出率 |
| 最大人脸 | 140px | 覆盖视频通话/自拍场景的典型人脸尺寸 |
| 最少票数 | 45 | 高门槛过滤纹理假阳性，用几何一致性替代置信度分数 |
| 步长比例 | 3.0 | 窗口数减少 89% vs. Δ=1.0，Haar 特征的空间冗余允许稀疏采样 |
| 缩放因子 | 1.25 | 论文推荐值，金字塔层数与尺度覆盖的最佳平衡 |

这套参数在 480×360 检测图像上实现了约 10~15fps 的有效检测帧率（含跳帧优化），视觉流畅度足以满足实时交互需求，同时保持了对正面人脸的可靠检出。

## 三、图片模式的三次重构历程

图片检测模式经历了三次架构变更，每一次都解决了一个特定的工程问题：

### V1：自动检测 + 防抖定时器（已废弃）
上传图片后自动触发检测，滑块变化时通过 200ms 防抖定时器延迟重新检测。问题：**定时器 + 异步检测 + 线程共享 Detector 导致难以调试的竞态崩溃**。

### V2：独立图片 Detector（已废弃）
为图片模式创建单独的 Detector 实例，避免与 VideoThread 共享。问题：**仍然崩溃**——根因不在 Detector 共享，而在 QImage 悬垂指针和 `stop_detection()` 超时处理不当。

### V3：手动触发 + 主线程同步（当前方案）
**根本性的架构简化**：
- 上传图片后不自动检测，用户点击按钮才触发
- 检测在主线程同步执行（VideoThread 已彻底停止）
- 无定时器、无防抖、无异步回调
- 五态按钮机管理所有用户交互路径

这次重构的教训是：**当异步逻辑的复杂度超过其带来的用户体验收益时，同步方案往往是更好的选择**。手动点击一次按钮的成本远低于排查一次随机崩溃的成本。

## 四、跨版本兼容性工程

### numpy 2.x → 1.x pickle 兼容

训练环境的 numpy 版本可能与推理环境不同。numpy 2.x 将 C 扩展路径从 `numpy.core` 改为 `numpy._core`，导致 pickle 反序列化时找不到模块。解决方案是自定义 Unpickler 在 `find_class()` 中做路径重映射：

```python
class _CompatUnpickler(pickle.Unpickler):
    def find_class(self, module, name):
        if module.startswith("numpy._core"):
            module = module.replace("numpy._core", "numpy.core", 1)
        return super().find_class(module, name)
```

### 模块路径别名

旧版训练代码以 `adaboost.StrongClassifier`（相对路径）序列化类对象，当前项目结构使用 `train.adaboost.StrongClassifier`（包路径）。通过在 `sys.modules` 中动态注册一个别名模块来桥接两种路径约定。

这两个兼容性补丁虽然只有不到 30 行代码，但避免了"必须用特定版本的 numpy 和特定目录结构运行"的运维噩梦——系统可以在任何安装了依赖的环境中直接启动。
